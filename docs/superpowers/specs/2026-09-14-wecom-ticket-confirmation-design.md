# 企业微信确认购票设计

## 目标

在现有 12306 抢票项目上新增一套“每日自动运行 + 企业微信卡片确认后才下单”的人工确认流程，同时保留原有立即抢票能力。

## 用户流程

1. 用户创建每日抢票任务，配置出发站、到达站、目标车次、席别、乘车人、每日启动时间以及乘车日期策略。
2. 到达每日启动时间后，系统自动计算当日目标乘车日期并启动监控。
3. 按现有 `query_interval` 周期查询指定车次和席别。
4. 发现可购买余票后，不立即提交订单，而是创建一次待确认记录并向企业微信智能机器人发送模板卡片。
5. 卡片显示车次、日期、出发到达站、发到时刻、席别和乘车人，并提供“确认预定”“忽略”按钮。
6. 用户点击“确认预定”后，服务端校验回调身份、任务归属、确认 token、状态和有效期。
7. 服务端重新查询一次目标车次与席别；仍有票才调用现有 `OrderService` 提交订单。
8. 订单提交成功后，通过企业微信通知用户前往官方 12306 完成支付；本轮任务停止。
9. 点击“忽略”、确认过期、余票消失或提交失败时，不创建订单；按任务策略继续监控或结束本轮。

## 任务模式

保留现有一次性任务模式，并新增每日任务模式：

- `schedule_mode = once | daily`
- `daily_start_time`：`HH:MM`，仅 `daily` 使用。
- `date_strategy = fixed | offset`
- `fixed`：继续使用现有 `train_date`。
- `offset`：每天启动时使用“中国时区当前日期 + N 天”计算乘车日期，`date_offset_days` 为非负整数。

每日任务在抢票成功后只结束当天运行，不永久改成 `SUCCESS` 后失效；下一自然日仍可再次被计划器启动。为避免混淆，任务长期状态和“当日运行状态”分开管理。

## 确认状态模型

新增确认记录 `TicketConfirmation`，与任务一对多：

- `id`
- `task_id`
- `token`：随机高熵一次性 token，仅保存摘要或使用不可预测值。
- `status = pending | confirmed | ignored | expired | consumed | failed`
- `train_date`
- `train_code`
- `seat_type`
- `seat_name`
- `seat_count_snapshot`
- `train_secret_snapshot`：只用于展示/诊断，不允许直接据此下单；确认后必须重新查询。
- `expires_at`
- `confirmed_at`
- `created_at`
- `details`

默认有效期 60 秒，可通过配置调整，最小 15 秒，最大 300 秒。

同一任务同一车次/席别在存在有效 `pending` 确认时不重复推送，避免刷屏。

## 企业微信智能机器人

新增独立 `WeComConfirmationProvider`，不把回调逻辑塞入现有通用 `notify.py`。通用通知模块继续负责普通成功/失败通知；确认 Provider 专门负责双向交互。

配置项：

- `WECOM_BOT_ENABLED`
- `WECOM_BOT_ID`
- `WECOM_BOT_SECRET` 或官方机器人要求的鉴权凭据
- `WECOM_BOT_CALLBACK_TOKEN`
- `WECOM_BOT_CALLBACK_AES_KEY`（若官方回调模式要求）
- `WECOM_CONFIRM_EXPIRE_SECONDS=60`
- `WECOM_ALLOWED_USER_IDS`：可选白名单；配置后只有白名单用户能确认。

优先采用企业微信官方支持的机器人/智能机器人事件与模板卡片能力。若部署方式使用 WebSocket 长连接，则 Provider 适配长连接事件；若使用 HTTP 回调，则暴露回调 API。核心确认服务不依赖具体传输方式。

## API 与事件边界

新增确认 API/事件处理层：

- 企业微信事件入口：处理 URL 校验、签名验证、消息解密和模板卡片按钮事件。
- 内部确认服务：`confirm(confirmation_id, actor_id)` 与 `ignore(confirmation_id, actor_id)`。
- 可选只读查询接口：查看任务当前待确认记录，便于前端展示和测试。

所有企业微信事件必须先完成签名/来源验证，再进入业务逻辑。按钮事件使用服务端保存的 confirmation id/token 映射，不能信任客户端传入的车次、席别或乘客信息。

## 下单安全约束

1. 发现余票时绝不直接根据第一次查询结果提交订单。
2. 用户确认后必须重新调用 `QueryService.query` 获取最新车次数据。
3. 必须再次匹配：日期、车次、席别、可购买状态、`secret_str`。
4. 只有确认记录为 `pending` 且未过期时允许进入下单。
5. 成功提交后原子地将确认记录标记为 `consumed`，防止重复按钮或重复回调导致二次提交。
6. 同一确认记录最多提交一次订单。
7. 不实现验证码绕过、限流绕过或支付自动化；支付仍在官方 12306 完成。

## 调度

复用现有 APScheduler：

- 现有 interval job 继续承担“运行中的任务按 N 秒刷票”。
- 为 `daily` 任务增加 cron job，每天 `daily_start_time` 触发一次。
- 服务启动时从数据库恢复每日 cron job。
- cron 触发时若当天已有正在运行或已成功提交的运行实例，则跳过，保证幂等。
- 中国时区为默认调度时区，继续使用项目现有 `SCHEDULER_TIMEZONE`。

## 数据库升级

现有项目使用 SQLAlchemy `create_all`，无法为既有 SQLite 表自动新增列。此次改动必须提供轻量数据库升级步骤：

- 启动时检测 `tasks` 表缺失的新列并执行兼容的 `ALTER TABLE ADD COLUMN`。
- 创建新的 confirmations 表。
- 升级脚本必须可重复执行，已升级数据库再次启动不得失败。

不引入完整 Alembic，避免为单次功能扩张依赖面；若后续模型继续增长再迁移到 Alembic。

## 错误处理

- 企业微信发送失败：记录日志，不直接下单；任务继续监控，并允许后续再次创建确认。
- 确认过期：标记 `expired`，继续监控。
- 用户点击忽略：标记 `ignored`，任务继续监控，但短时间内对同一车次/席别增加冷却，避免立即再次推送。
- 二次查询无票：确认标记 `failed`，通知“余票已变化”，继续监控。
- 登录过期：沿用现有逻辑停止运行并通知重新登录。
- 下单失败：记录真实原因并通知；除明确不可恢复错误外，允许任务继续监控。

## 测试

至少覆盖：

1. daily 任务每天按配置时间注册 cron job。
2. offset 日期策略按中国时区正确计算。
3. 发现余票后 `auto_submit` 不直接下单，而是创建 pending confirmation。
4. pending confirmation 去重。
5. 过期 confirmation 拒绝下单。
6. 非白名单用户不能确认。
7. 重复按钮/重复回调只允许一次下单。
8. 用户确认后会重新查询，余票消失时不提交订单。
9. 二次查询仍有票时调用现有订单服务，并在成功后发送支付通知。
10. 数据库升级脚本对旧库和已升级库均可重复执行。

## 首版范围

首版只实现企业微信智能机器人确认，不实现个人微信非官方协议 Bot，不实现短信，不实现自动支付。前端只做支持创建/编辑每日任务和展示确认状态所需的最小改动，优先保证后端链路和 Docker 部署可靠。
